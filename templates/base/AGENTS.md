## 0. 禁止事項

- **`.env` 系ファイルを編集・生成・コミットしない**（`*.example` を除く）。設定変更が必要なら `*.example` の更新と説明に留める。
  - 由来: 実環境の秘密を AI が触ると、漏れる側は静かに起きる。`.claude/settings.json` でも機械的に止めている。
- **本番環境を直接操作しない**（デプロイ・DB 書き込み・実ユーザーへの通知）。本番向けコマンドは人間が打つ。
  - 由来: MCP が本番プロジェクトを指したまま、削除・配信まで届く状態になっていたことがある。

## 1. 品質ゲート

- **`test` / `lint` / `typecheck` は最初のコミットから緑にしておく。** 空のアプリに対して先に通しておくこと。
  - 由来: ビルドすら通らないコードが数週間コミットされ続けたことがある。別プラットフォームしか触っていなかったので誰も気づかなかった。壊れるものが無いうちに「壊れたら分かる」を作る。
- **TDD を既定とする。** ビジネスロジックとセキュリティ境界（入力のサニタイズ・パス解決・暗号）はテストを厚く。
  - 由来: AI に書かせる開発では、人間に残る仕事が「結果を見に行くこと」になる。見に行く場所が要る。
  - 外してよい: 一人で全部頭に入る規模の実験なら。外したら [docs/GRILL.md](docs/GRILL.md) の「外した既定」に書く。
- **書いた AI に検品させない。** レビューは別セッション（可能なら別モデル）で、齟齬・幻覚・欠落を分けて探し、根拠のファイル名と行番号を必ず添えさせる。示せない項目は「推測」と明記させる。
  - 由来: 同じセッションに「合ってる？」と聞くと、書いたときの思い込みのまま「合ってます」と返る。実測で確認済み。

## 2. 作業ルール

1. **変更はタスクに必要な範囲に留める。** 無関係なリファクタ・未依頼のドキュメント追加はしない。
2. **仕様変更は仕様とコードをセットで。** 仕様の正本は `docs/specs/`（無ければ作る）。
3. **1巡ごとにコミットする。** 探す → 直す → 直した箇所だけ再検証 → 次へ。どのバージョンへの指摘かを見失わないため。
4. **成功判定は状態の実測で取る。** 終了コードやメッセージではなく、成果物・画面・`du`・`ps` を見てから「終わった」と言う。
   - 由来: exit 0 を返しながら何も消していないコマンドを「完了」と報告したことがある。
5. **不可逆な操作の前には止まる。** 削除・上書き・公開・課金・名義変更は、「何回まで／外したらどうなる／どこで止めるか」を添えて人間に渡す。
6. **推測には出典と確度を添える。** 実測した範囲だけを「確認した」と書く。
   - 由来: エージェントの推測が断定形で文書に定着し、次のセッションがそれを既知の事実として扱った。
